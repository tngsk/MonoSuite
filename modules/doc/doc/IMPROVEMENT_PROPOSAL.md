## 提案の要旨

Monoの「Markdownから持ち運べる単一HTMLを作る」という価値を維持し、安全な変換、正確な出力結果、再現可能な利用ガイドを整備する。

最初に、メディアの読込制限とPDFの失敗処理を修正する。続いて静的出力を保証し、共通構文を統一する。文書は、動作する利用例と提供済み機能を正確に説明する内容へ更新する。Node依存と参加者同期については、実装着手前に方針を記録する。

本提案は実装変更の承認を意味しない。現時点で作成した成果物は本書のみであり、既存の設計正本やアプリケーションは変更していない。

## 背景と到達目標

調査では、許可範囲外のダミーファイルがHTMLへ埋め込まれること、`minimal`でも実行用JavaScriptが出力されること、PDF生成失敗が変換成功として返ることを確認した。また、利用ガイドには未実装機能や変換できない記法例が含まれる。

既存テストは調査時点で312件、サブテスト12件すべて成功している。改善では、今回の差分を検出できる検証を追加し、次の状態を目指す。

| 目標 | 完了を判断する条件 |
|---|---|
| 安全に配布できる | 許可範囲外のファイルと未許可のPythonコンポーネントを読み込まない |
| 出力結果を信頼できる | 指定されたPDF生成やデータ送信に失敗した際、成功と表示しない |
| 静的配布を選べる | `minimal`で本文・コード・ローカル画像をJavaScriptなしで閲覧できる |
| ガイドをそのまま使える | 公開例が期待する要素・属性・出力ファイルを生成する |
| 提供範囲を判断できる | オフライン機能、オンライン依存、模擬機能、開発中機能を区別できる |

## 改善施策

優先度P1は次の機能拡張より先に対応する事項、P2はその後の整合性・操作性改善を示す。

### A. ファイルとコンポーネントの読込制限を復元する

**優先度: P1 / 調査報告: 項目1・2 / 作業規模の目安: 中**

メディアパスを正規化し、Markdownディレクトリまたは作業ディレクトリの許可範囲内であることと、通常ファイルであることを検証する。範囲外参照は埋め込まず、対象を示した診断を出す。許可範囲内の `../assets/` は引き続き利用可能とする。

コンポーネントは明示的な許可リストを入口とし、その対象だけをインポートする。マニフェストによるカテゴリ・状態・必要アセットの管理は維持する。マニフェストの存在をロード許可の代わりにしない。

主な対象は [media.py](/Users/ngsklab/Code/Mono/src/embedders/media.py)、[registry.py](/Users/ngsklab/Code/Mono/src/registry.py)、[constants.py](/Users/ngsklab/Code/Mono/src/constants.py)、[markdown.py](/Users/ngsklab/Code/Mono/src/processors/markdown.py)。

**受入条件:** 実在する調査用ファイルを用い、範囲外の相対パス・絶対パス・シンボリックリンクを拒否する。範囲内画像は成功する。未許可コンポーネントのインポート処理が呼ばれず、既存の許可済みコンポーネントは変換できる。

**移行上の注意:** プロジェクト外の画像を直接参照している入力は修正が必要になる。許可範囲へ素材を移す手順を案内する。

### B. PDFとデータ送信の成功判定を正す

**優先度: P1 / 調査報告: 項目4・関連不整合 / 作業規模の目安: 小〜中**

PDF生成の失敗を変換結果とCLI終了コードへ伝播させる。HTMLとPDFの出力先が正規化後に同一になる指定は、書込み前に拒否する。正しい利用例は以下とする。

```sh
uv run main.py document.md -o document.html --pdf document.pdf
```

データ送信は、まずmono-export側でHTTP結果と応答JSONの `status` の両方を確認する方式を推奨する。APIのHTTPステータス体系を変える案は、既存クライアントへの影響を確認した上で別途判断する。サーバーの成功応答は現状ではキューへの受付であるため、ディスクへの保存完了を保証する表示にはしない。

主な対象は [converter.py](/Users/ngsklab/Code/Mono/src/converter.py)、[config.py](/Users/ngsklab/Code/Mono/src/config.py)、[main.py](/Users/ngsklab/Code/Mono/src/main.py)、[mono-export/script.js](/Users/ngsklab/Code/Mono/src/components/mono-export/script.js)。

**受入条件:** PDF失敗でCLIは非ゼロ終了し、HTMLの生成成否を区別して案内する。同一出力先の指定で既存ファイルを上書きしない。HTTP 200でも `status: error` なら成功表示しない。通信失敗・不正JSON応答も失敗として扱う。

### C. `minimal`の静的出力を実装する

**優先度: P1 / 調査報告: 項目3 / 作業規模の目安: 大**

正式名称を `minimal` に統一し、通常のHTML/CSS、静的コード表示、直接埋め込み画像で構成する出力経路を設ける。JavaScriptによる画像の復元やShadow DOMの生成を前提としない。スクリプトを最後に削除するだけの対応は避ける。

初期対応は標準Markdownの本文・見出し・表・コード・ローカル画像を保証範囲とする。コンポーネントは静的代替を検証できたものから対応表へ追加する。未対応のコンポーネントを含む入力は、内容を黙って落とさず、対象名を示して変換を終了する案を推奨する。

未知のプロファイルはエラーにする。READMEに掲載されていた `static` は移行期間の警告付き別名として `minimal`へ解決する案を推奨する。別名の終了時期はリリース方針と合わせて決める。

主な対象は [config.py](/Users/ngsklab/Code/Mono/src/config.py)、[converter.py](/Users/ngsklab/Code/Mono/src/converter.py)、[html.py](/Users/ngsklab/Code/Mono/src/processors/html.py)、[media.py](/Users/ngsklab/Code/Mono/src/embedders/media.py)と静的出力用テンプレート。責務分割を具体化してから着手する。

**受入条件:** 保証範囲の入力から生成したHTMLに実行用script、インラインイベントハンドラー、JavaScript URLがない。JavaScript無効・ネットワーク遮断のブラウザで本文・表・コード・画像が読める。未対応要素と未知プロファイルを検出する。standard/presentationの既存動作は回帰テストで維持する。

### D. 共通構文と明示ラベルを一貫させる

**優先度: P2 / 調査報告: 項目5・関連不整合 / 作業規模の目安: 中**

単独コンポーネントの後置属性 `@[...](...){.class #id}` を共通規則で解釈する。既存の丸括弧内 `class:` / `id:` は維持する。競合時はクラスを重複除去して結合し、IDは後置属性を優先する案とする。HTML属性値のエスケープを共通処理で保証する。

リンクカードは、明示されたラベル、OGPタイトル、URLの順で表示タイトルを決める。OGP取得失敗でも明示ラベルを保持する。

主な対象は [base_parser.py](/Users/ngsklab/Code/Mono/src/processors/base_parser.py)と各コンポーネントのパーサー。

**受入条件:** badge/linkを含む対応コンポーネントで波括弧が本文に残らず、class/idが意図した要素へ付く。引用符を含む属性も安全に出力される。コードブロック中の記法例は変換されない。OGPの有無によらず明示ラベルが優先される。

### E. 文書を検証済みの利用方法へ更新する

**優先度: 誤操作・安全性に関わる訂正はP1、その他はP2 / 調査報告: 項目6〜11 / 作業規模の目安: 中**

| 文書 | 更新内容 |
|---|---|
| README | PDFコマンド、プロファイル名、既存distへの出力、流体余白、スライド移動条件、オフライン範囲 |
| 記法ガイド | 段落への文字サイズ指定、badgeのcolor引数、終了タグが必要な構文の区別、属性構文の対応範囲 |
| 教育系機能の説明 | 単一選択投票、4グループ固定、セッションID手入力、模擬ログイン、JSONダウンロードの実態 |
| 開発指示 | JSONエスケープの正しいPython例、現在のCSSトークン・注入条件・コンポーネント状態 |
| 起動・導入説明 | `uv run python -m src.server`、任意の図・数式描画依存、PDF用ブラウザ準備 |
| マニフェスト説明 | exportのJSONL/CSV表記など、実際の機能との不一致 |

新機能の実装が必要な説明は、対応完了後に公開する。未実装のCSV出力、QR表示、実認証、リアルタイム集計を文書整合のために新設することは、本改善の範囲に含めない。

**受入条件:** 各公開例が期待するHTML・属性・出力パスを生成する。表示形式のBlockと終了タグ必須のコンテナ構文が区別される。文書の機能説明と実装の対応表に未解決の矛盾がない。過去のCHANGELOGは履歴として保存し、新たな変更は新しい項目に記載する。

## 設計判断の推奨案

以下は実装承認と合わせて確定する方針であり、現行仕様として断定しない。

| 論点 | 推奨案 | 代替案と影響 |
|---|---|---|
| Node依存 | 基本変換はPython。数式・図の事前描画でのみ任意のNodeを許可し、配布先では不要とする | 純Pythonへ全面移行すると描画方式の置換と互換性検証が必要 |
| mono-sync廃止後 | 既存SSE APIを維持し、標準の参加者同期クライアントは未提供と明示する | 新クライアントによる同期復活は、セッション分離・送信責務を含む別設計が必要 |
| オフライン保証 | ローカル埋め込みの基本コンテンツを保証。CDNや外部画像への依存を一覧化し、依存が残る出力は診断する | 全機能完全オフラインはCDN除去・静的代替・容量検証まで必要 |
| minimalの未対応要素 | 初期版は対象を示してエラー終了。静的代替を段階的に追加する | 全要素の静的代替を初回に揃えると対応範囲と検証量が大きくなる |
| 設計正本の整合 | 別の設計変更記録に判断と正本との差を残し、正本の改訂方法を明示的に決める | 正本だけを実装に追従させると、不変とする現行ルールに反する |

`doc/ARCHITECTURE.md` の変更と、保護対象であるconverter/main/html等の変更は、対象範囲を明示した承認後に行う。

## 検証・レビュー手順

実装時は、変更対象の最新版を `cat` / `rg` で確認し、変更後も `cat` と `git diff` でファイル内容を確認する。調査で再現した入力をテスト用の一時ディレクトリに作り、期待結果を検証する。

1. `uv run pytest -q --tb=short` で既存テストと追加した契約テストを実行する。
2. `uv run main.py <検証用Markdown> -o <一時出力HTML> -p minimal` とstandard/presentationの比較変換を行い、Playwrightで閲覧・操作・静的表示を検証する。
3. `uv run main.py <検証用Markdown> -o <一時出力HTML> --pdf <一時出力PDF>` で正常出力を確認し、PDFプロセッサー失敗のテストで非ゼロ終了を確認する。
4. `git diff --check` と `git diff` を用いて差分をレビューし、生成したHTML/PDFをコミット対象へ含めていないことを `git status --short` で確認する。
5. Complete pre-commit steps to ensure proper testing, verification, review, and reflection are done.

最終レビューでは、受入条件との対応、互換性への影響、残る制約を検証記録に記す。既存テストの成功数のみを完了条件にしない。
