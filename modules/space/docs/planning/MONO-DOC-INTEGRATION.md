Docの仕様書を読んだレビューであり、Docのソースコード・実行結果は未検証。以下の「Doc仕様」は文書上の記載を示す。参照元は変更していない。Suiteへの統合、記法変換、PDF処理の変更もまだ行っていない。

## 1. 前提の更新

Suiteの中心目標は「1つの原稿から、Spaceで発表し、Docで配布資料を出力する」。配布を主目的にDocから書き始める使い方も同等に扱う。初期統合ではSpace原稿→Doc HTML・PDFを最優先の機能とする。画面の印刷ではなく原稿から再組版し、DocはMarkdown順に読む構造とする。内容を保持する出力規則は[リリース方針](RELEASE-STRATEGY.md)を正とする。

Docは新規作成する文書エンジンではなく、既存の縦スクロール型生成器として取り込む。仕様には静的HTML、プレゼンテーション用ズーム、PlaywrightによるPDF、任意の対話コンポーネントと同期サーバーが含まれる。

Suiteは引き続き1アプリ・3モジュールを目指す。ただし初期統合は、既存DocとSpaceを別エンジンのまま呼び出す薄い共通窓口にする。共通ASTや新しいレイアウト記法の導入を統合の前提にしない。

| 領域 | 統合方針 |
|---|---|
| Doc | 縦に読む文書とPDF。既存プレゼンテーションモードは維持し、Spaceの操作体系へ即座に置換しない |
| Space | 空間に配置してフォーカスするプレゼンテーション。PDF・Docの対話機能を移植しない |
| Lib | ファイル一覧、アセット、インポート、出力処理の呼び出し。講義の投票・認証・同期サーバーはLibの責務にしない |
| 共通化 | まずファイルとアセット、警告・エラーレポート、出力結果の契約。その後に実際に一致する処理を抽出 |

## 2. 記法と描画の差

| 項目 | Doc仕様 | Space現状／統合判断 |
|---|---|---|
| 基本構造 | HTML見出しと縦スクロール | H1タイトル・H2横の章・H3縦の話題。意味は共有できても配置は別 |
| 明示レイアウト | `::: hbox/vbox/compare/section` | `::layout row/stack/compare/flow`。自動的な同一視をしない |
| 比較 | 2・3要素の等幅 | 2・3要素の比較。対応候補だがフェンス内見出しの扱い・範囲を先に確定 |
| tone | 意味名8種 | 名前は概ね一致、secondary・info・errorなど色は異なる。役割名を共有し、色値はテーマ別 |
| marker・note | 見出し帯、枠・左線付きnote | 適用範囲と外観は各レンダラーに残す。Spaceのフォーカス枠と混同しない |
| 組版 | 本文42em、justify、pretty | 本文512px、通常折り返し。Spaceで合意済みの通常折り返しを維持 |
| グリッド | 16pxと3×3スケール | Space32px。役割は共有候補、数値の統一は不要 |
| HTML要素 | `dl`、`details` | Spaceで同等の対応を前提にしない。未対応は警告または内容保持の変換を設計 |
| インライン装飾 | `== ==`、`++ ++`、`{{ }}` | 現在のSpace共通記法ではない。最新Doc入力を無条件に直接渡さない |
| 接続線 | `#id`とラベル、tone属性 | Spaceと属性文法が異なる。ID解決とラベル保存のテストが必要 |
| コード | ハイライト＋コピー | Spaceは装飾なし。印刷用のコードは別途原文保持を検証 |
| 数式 | 参照仕様に記載なし | Spaceは生成時SVG。Docが未対応と断定せず、統合前の確認項目とする |
| 対話機能 | opt-inの投票、認証など | Suite最小版の必須機能にしない。必要なサーバー・通信条件を別途明示 |

標準Markdownの対応範囲も同一とは限らない。共通原稿からDoc／Spaceへ出力できることを目指しつつ、当初はモジュール固有の記法を含む場合に変換レポートを表示する。無損失の往復変換は約束しない。

## 3. 既存Monoインポーターの位置づけ

Spaceの`mono_import.py`を確認したところ、主な変換対象は旧`@[section]`、`@[flow]`、badge、textfield等。最新Docの`:::`レイアウトを変換する専用処理はない。現在の`--from mono`を「最新Mono Doc完全対応」と表記しない。

当面は旧Mono入力用として範囲を明記する。最新Docへの対応時は、レイアウト、強調、HTML要素、接続線、テーマ、対話機能を含む小さな入力fixtureを作り、対応・内容のみ保持・非対応を区別する。原本を変更せず、行番号と失われる機能を報告する。形式判別は明示指定を基本とし、推測だけで誤変換しない。

## 4. PDF・ランタイム方針の修正

既存の`--pdf`とPlaywrightを初期統合で維持する。前案のElectron `printToPDF`への置換は行わない。Electronはアプリ外枠の候補であり、PDFエンジンとは独立の選択とする。

ElectronとPlaywright用ブラウザーを同梱すると容量・更新対象が増える可能性がある。まず既存経路の再現性を確認し、その後、同梱構成を比較する。開発時の`uv`等の依存と、利用者向けアプリのランタイムを区別し、利用者に開発環境の手動準備を要求しない。

PDF受け入れ条件：

- 日本語とコードをmacOSのプレビューでコピーし、元文字・改行・空白・インデントを比較する。ハイライトなしの印刷表現を第一候補にし、既存ハイライト経路との比較で判断。
- フォント指定だけで問題解消を保証しない。未インストール環境、実際の埋め込み・代替フォント、文字抽出結果を確認する。
- 閉じた`details`の内容も出力されることを確認する。`display:block`の記述だけで展開済みと判定せず、必要なら生成時に`open`を付ける処理を検討。
- 用紙サイズ、余白、表・コード・画像の改ページ、長文の分割規則を明文化する。「モノリシック」が単一ファイルか長尺1ページかを確認する。
- 入力・投票などの非表示部分について、本文や回答が失われる条件を明示する。

## 5. Doc仕様書で確認・整理したい点

ここでは仕様の矛盾や未定義箇所を指摘する。実装不具合と断定せず、Doc側の実装確認後に正本を更新する。

1. **文字サイズの3段階**：display/body/compactに加え、見出しではtitle 28px、subtitle 20pxが登場する。「3つの用途分類＋見出し派生値」とするのか、5段階なのか整理する。流体スケールの最小・最大値も未記載。
2. **余白の3段階と16pxグリッド**：112・64・23pxに加えxs 8px、未定義のmdを使用する。23pxを光学補正として残すならグリッドの例外と記載する。単純に24pxへ丸める変更はしない。
3. **`:::`の区切りと終端**：同じ単独行をカラム区切りと終了に使うため、何をもって終了と判定するか、通常本文への復帰、入れ子、コード内のリテラル、不正入力を定義する。Suiteで複雑な入れ子仕様を追加しない。
4. **標準Markdownの範囲**：「忠実に解釈」だけでなく、採用パーサー・拡張・生HTML許可範囲を列挙する。Suiteのプレビューから任意スクリプトを実行させない。
5. **Zero-JSと対話機能**：minimal時のリッチリンク・ズーム・接続線・入力系の静的表現と、通信・サーバー必須条件を対応表にする。opt-inが何の指定で有効になるかも必要。
6. **テーマ設定の優先順位**：Docの`@[theme: corporate]()`と将来の`mono.json`が競合しないよう、設定ファイル仕様を確定する前に優先順位を決める。
7. **ID・接続線**：重複ID、存在しない参照先、PDF時の線、引用符やラベルの構文を定義する。
8. **欠損アセット**：Docは表示エラーの仕様。Suiteは警告付き成功と生成失敗を区別し、画像欠落を成功表示だけで隠さない。原稿の42emは日本語文字数の厳密保証ではないため目安とする。

## 6. 次の作業順序

1. Spaceのv0.1基準点を作る。Docの統合を待って基準点を作り直さない。
2. Docリポジトリの実装・依存固定ファイル・テスト・公開可能素材を調査し、仕様書の不明点を実装と照合する。
3. Doc自身の参照コミット・版を記録して`modules/doc`へ独立移行。現在のCLI・PDFを同じ入力で再現する。
   この段階で元原稿と出力見出しの対応、診断、入力版の契約を小さく決める。共通ASTは必須にしない。
4. Space原稿からDoc HTML・PDFを出力する処理を最優先で作る。既存解析器は維持し、必要な変換は生成時の派生データとして扱う。Doc用原稿の二重管理を要求しない。
5. 同じ原稿の本文・素材・数式・比較・工程・接続線の説明がDocで保持されるfixtureを整備する。未対応は警告し、発表順と読む順序の分離を検証する。
6. Lib／アプリ外枠からDoc／Spaceをプレビュー・出力する。Docから書き始める経路も維持し、最新Doc→Spaceの対応範囲を拡充する。合意した範囲から共通処理を抽出する。

配布セット生成の処理は手順4〜5で先に検証する。手順6では位置保持切り替え、保存時プレビュー、配布セットUIの順に加える。作例と公開リンクの時期・受け入れ条件は[開発計画](DEVELOPMENT-PLAN.md)を参照。
