## 1. 機能を加えるタイミング

| 段階 | 実施内容 | 完了条件 |
|---|---|---|
| A：v0.1保存 | 現状の整理、新規リポジトリ、既知の問題の記録 | コピー先で再現可能。追加機能を待たず基準点を残す |
| B：統合前の小さな設計検証 | Doc実装確認、対応範囲、原稿位置、生成結果の契約を決める | 代表原稿1本で変換範囲と未対応を説明できる |
| C：最初の統合成果 | Space原稿→Doc HTML・PDF、診断、配布セット生成の処理 | 同じ入力版から3出力を生成し、失敗時に既存セットを壊さない |
| D：制作環境の試用版 | 現在位置を保つDoc／Space切り替え、続いて保存時プレビュー、配布セットUI | 編集・切り替え・書き出しの一連操作が成立 |
| E：試用結果を反映 | 小さな作例のコピー／挿入 | 記法を暗記せず代表的な表現を作れる |
| F：初回リリース後 | 配布資料からSpaceの同じ話題へのリンク、必要ならQR | 公開先と永続アンカーの扱いを確定してから提供 |

5案は計画に採用するが、すべてを初回リリースの条件にしない。現在位置保持・保存時プレビュー・配布セットを試用版の中心とし、作例の専用UIと公開リンクは後続とする。配布セットの処理はCで先に作り、利用者向けの操作はDで加える。

## 2. 本開発前に決める最小限の契約

### 原稿と表示位置

両レンダラーが同じ原稿の見出しを識別できるよう、元のファイル・見出し・ソース範囲と、出力側の要素との対応表を持つ。完全な共通ASTは必要ない。中間変換で行番号や見出しが変わる場合も、元原稿への対応を保持する。

初期の位置保持は見出し単位。Spaceで画像等を見ている場合は所属する話題へ、Docでは画面上端付近の見出しへ対応させる。Doc→Spaceは対応する話題をフォーカスする。切り替え前の各ビューの状態を保持し、不要なカメラ移動を避ける。

同じ原稿版での対応は確実にする。編集後は明示IDがあれば優先し、なければ見出しの階層・内容等で照合する。削除や重複で特定できなければ親または近い前方の見出しへ戻す。単純な連番だけを永続IDにしない。アルゴリズムは重複見出し・改名・挿入・削除のfixtureで決める。

原稿へ自動でIDを書き込むことは要求しない。セッション内の位置保持と、公開後も有効なURLアンカーは別仕様。後者はFまで確定を急がない。

### 出力対象と診断

標準本文、画像、表、コード、数式、比較、工程、接続線ラベルを最初の対応表にする。Docは原稿順に読む。対話機能やレイアウトの非対応を黙って落とさない。

結果は成功・警告付き成功・失敗を区別し、問題には対象形式、元原稿の位置、理由を付ける。致命的な変換エラーと必須画像欠落は正式な配布セットの更新を止める。OGP取得失敗で通常リンクにできる場合など、内容を保持できる代替は警告付きで出力可能とする。

本文が失われる未対応機能は警告だけで正常完了にしない。原文を表示する等の代替を定義するか、配布出力を止める。プレビューは問題箇所を示せても、配布可能な完成品と区別する。確認ダイアログを毎回出さず、問題があるときだけ短く表示する。

### 入力版と更新

原稿、参照アセット、出力設定を1回の生成の入力版として固定する。ビルドIDでプレビューと成果物の対応を識別する。キャッシュや生成物の更新が監視を再発火しないよう、入力と出力の場所を分ける。

保存時プレビューはファイル保存後の更新に限定する。連続保存をまとめ、古いビルドの完了が新しい結果を上書きしないようにする。生成失敗時は直前の正常な表示を残し、「更新できていない」ことを控えめに示す。正常な結果がない初回はエラー表示とする。

全体表示やフォーカス状態、表示位置を維持する。既存の一時付箋を更新で誤って消さないよう、原稿描画とセッションUIの寿命を分ける方針を検証する。付箋の永続保存や配布物への埋め込みは追加しない。

### 配布セット

```text
教材名/
  presentation.html
  handout.html
  handout.pdf
```

3形式は同じ入力版から生成する。生成中は一時領域を使い、検証済みのセットだけを完成品として公開する。一部失敗時に新旧の成果物を混ぜない。出力名と置き換え方法はCで実装・テストする。

原稿・アセットを含む編集用パッケージは別操作とし、通常の配布セットに含めない。個別形式の出力も残す。PDF生成を毎回の保存時プレビューで必須にせず、まず画面プレビューを更新し、PDFは明示的な確認・書き出し時に生成する。

## 3. 作例挿入と公開リンク

作例はCの検証fixtureを兼ねて作る。比較2項目・画像3枚・工程・引用を少数用意し、両出力の結果を確認する。Eではまずコードをコピーするだけの操作を提供できる。外部エディターのカーソル位置へ自動挿入できるとは約束しない。独自コンポーネント編集画面や新しい保存形式は作らない。

配布HTMLからSpaceへのリンクは同じ配布セット内の相対リンクを候補にする。PDFのリンク・QRは公開URLを明示設定した場合だけ作成し、ローカル絶対パスを配布物に入れない。アプリによるホスティングは必須にしない。アンカーの永続性、更新・改名時の振る舞い、リンク切れの確認をFの前提とする。設定がなければリンクUIは表示しない。

## 4. 検証と範囲の歯止め

- Bの成果物は短い対応表・処理結果の仕様・代表fixture。包括的なパーサー統一や公開プラグインAPIの設計まで広げない。
- C：元原稿の内容・参照の保持、3出力の入力版一致、PDFのコピー品質、1形式失敗時の既存成果物保護を確認。
- D：同じ話題への往復、画像からの切り替え、見出しの挿入・削除・重複、連続保存、失敗後の復帰、一時付箋の維持を確認。
- UIは通常1ビュー＋Doc／Space切り替え。常時2画面表示や新しいパネルを必須にしない。
- 出力先ごとの本文条件記法、高度なエディター、クラウド同期、投票・認証統合は今回の追加範囲に含めない。
- スケジュールは日付ではなく上記の完了条件で区切る。BのDoc実装確認後に工数を見積もる。

参考にした既存の設計：Quartoの[変更監視プレビュー](https://quarto.org/docs/cli/preview.html)と[複数出力形式](https://quarto.org/docs/reference/formats/)、RStudioの[Markdownを保持する視覚編集](https://docs.posit.co/ide/user/ide/guide/documents/visual-editor.html)。それらの機能全体を移植する計画ではない。
