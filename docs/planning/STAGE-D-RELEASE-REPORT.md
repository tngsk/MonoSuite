## 1. 段階Dの目的と背景

段階D（制作環境の試用版）は、発表用スライド（Space）と配布用文書（Doc）の執筆体験を単一の統合環境として確立し、執筆者がストレスなく両形式の内容整合性を確認・同期できるローカル開発基盤を提供することを目的とする。従来の制作工程では、スライド用と文書用で別々のツールを起動して原稿の重複編集を強いられるか、ビルドのたびに重厚なPDF生成待ちが発生して執筆のリズムが寸断されるという深刻なアクセシビリティの乖離が存在していた。この課題に対し、本段階では外部エディターによるMarkdown保存をトリガーとした0.4秒台の超高速自動プレビュー、全画面表示と瞬時のビュー切り替え、および双方向の見出し位置同期を実現する軽量サーバー環境をリデザインした。これにより、執筆者は手元の慣れ親しんだエディターで執筆に集中しながら、ブラウザ上でリアルタイムに発表用・配布用の双方の仕上がりをシームレスに行き来できる実用的な制作フローを確立した。

## 2. 実装アーキテクチャと主要コンポーネント

段階Dの実装は、単一責任の原則に基づき、外部ライブラリへの過度な依存を排してPython標準のネットワーク・並行処理モジュールを活用した堅牢な設計を採用した。

1. 統合プレビューシェル（src/mono_suite/shell/）：
   ブラウザ上の画面上部に常駐するミニマルなヘッダー（約40px高）と、全画面iframe表示領域で構成されるWebフロントエンド。ビュー切り替えボタン（Space/Docトグル）、配布PDF書き出しボタン、および接続ステータスインジケーターを備える。
2. 位置同期およびイベント制御スクリプト（src/mono_suite/shell/sync.js）：
   ビューの切り替えが発生した瞬間にのみ、直前に閲覧していたアクティブ見出しIDを取得し、切り替え先のビューに対してカメラ移動またはスクロールを実行する同期ロジックを提供する。Space側は目次ボタン（button[data-section=ID]）のクリックイベントを発火させて既存のカメラ制御を呼び出し、Doc側は対象要素（getElementById(ID)）へのscrollIntoViewを実行する。常時同期による画面のバタつきやカメラの乱れを防止し、切り替え時の文脈維持に特化した快適な操作性を担保した。
3. ローカル開発サーバー（src/mono_suite/server.py）：
   Python標準のhttp.server.ThreadingHTTPServerを拡張したDevServer基盤。静的ファイル配信、iframe内での閲覧用ルート（/space, /doc）、ビルド成果物メタデータ（/manifest）、ブラウザへのリロード通知を行うServer-Sent Eventsエンドポイント（/events）、および完全ビルドを指示する書き出しAPI（POST /api/build）を提供する。
4. ファイル保存監視モジュール（src/mono_suite/watcher.py）：
   指定されたMarkdown原稿および同一階層の関連アセット（画像等）の更新日時（mtime）を独立スレッドで監視するFileWatcher。外部エディターによる保存を検知すると、PDF生成を省略した--no-pdfパイプラインを即座に呼び出し、生成完了後にSSE通知キューへリロードシグナルを発行する。
5. 静的プレビューサーバー（src/mono_suite/server.py内のServeServer）：
   完成した配布セットディレクトリ（dist/など）を読み取り専用でホストする軽量サーバー。
6. CLIサブコマンドの拡張（src/mono_suite/cli.py）：
   制作監視サーバーを起動するmono devコマンド、および配布セットをプレビュー配信するmono serveコマンドを実装。

## 3. 位置同期機構と高速更新の技術的検証

段階Dにおいて設計した各機能は、実際の利用シナリオを想定した計測とDOM検証において極めて高い安定性を記録した。

1. 0.4秒台の超高速自動プレビュー：
   外部エディターでMarkdown原稿を保存した際、Playwright Chromiumを起動しない高速ビルドパイプラインが実行され、0.3秒から0.4秒台でHTML生成とSSEイベント送信が完了する。ブラウザ側はsync.jsにより現在のアクティブ見出し位置を保持したままリロードされ、執筆の流れを途切れさせないリアルタイムな反映を確認した。
2. 双方向の位置同期インターフェース：
   Space表示中にDocへ切り替えた場合、Spaceの目次で選択されているノードID（#section-toc button[aria-current=true]）を抽出し、Docの該当見出しへスムーズスクロールする。Doc表示中にSpaceへ切り替えた場合、スクロール領域の可視見出しIDを特定し、Spaceの対応目次ボタンをクリックしてカメラを該当ノードへジャンプさせる。この切り替え時限定の同期方式により、レンダラー固有の内部状態を破壊することなく、直感的な文脈保持を実現した。
3. オンデマンドPDF書き出し：
   執筆中の通常保存ではPDF生成を行わず、ヘッダーの「配布PDF書き出し」ボタンまたはAPIリクエストが実行された場合のみ、Playwrightを起動した完全ビルドを実行する。ビルド中にはボタンが「PDF出力中...」となり二重実行を抑制、完了時には「配布PDF出力完了」の通知とともに成果物が確定される動作を検証した。

## 4. テスト結果と定量的エビデンス

新規に作成した段階D統合テストスイート（tests/test_stage_d_authoring.py）および既存の全テストスイートを実行し、全件合格を確認した。

1. 静的プレビュー配信テスト（test_serve_server_delivers_files_and_redirects）：
   配布セット（presentation.html, document.html, document.pdf, build-manifest.json）がmono serve経由で正確に配信され、ルートアクセス時にpresentation.htmlへリダイレクトされることを確認。
2. 開発シェルUIおよび配信ルーティングテスト（test_dev_server_routes_and_shell_content）：
   mono dev起動時に、ルートURLで統合プレビューシェルHTMLが返され、/space, /doc, /manifestがそれぞれのコンテンツを正確に提供することを確認。
3. 完全ビルドAPI実行テスト（test_dev_server_build_api）：
   POST /api/buildへのリクエストにより、PDFを含む完全ビルドが同期実行され、200 OKレスポンスとともに最新のマニフェスト情報が返却されることを確認。
4. ファイル監視および自動リビルドテスト（test_watcher_detects_change_and_triggers_rebuild）：
   原稿ファイルのタイムスタンプ更新をFileWatcherが0.5秒以内に検知し、コールバック経由でリビルドおよびSSEリロードシグナルが正常発行されることを確認。
5. 全体リグレッション検証：
   Space単体テスト全67件、Docテスト全271件、段階B3契約テスト全7件、段階Cパイプラインテスト全5件、段階Dテスト全4件の合計354件の全テストが一切のエラーなく合格。

## 5. 段階Eへの引継ぎ事項

段階Dにより、単一原稿からスライドと文書を同時に編集・確認・出力するローカル開発体験が完成した。最終段階となる段階E（品質検証と実用化）に向けて、以下の項目を引き継ぐ。

1. 外部サンプル原稿による網羅的検証：
   数式（LaTeX/KaTeX）、コードブロック、大容量画像、複雑なテーブル等を含む実践的な技術ドキュメント原稿を投入し、プレビュー表示やPDF改ページ位置の崩れがないか検証する。
2. プラットフォーム互換性の確認：
   macOS環境に加えて、Linux環境におけるChromiumヘッドレス実行やファイル監視の互換性を確認し、必要に応じた環境依存コードの吸収を行う。
3. 配布パッケージングとドキュメント完備：
   CLIツールとしてのインストール手順、コマンドリファレンス、およびトラブルシューティングガイドを整備し、第三者が即座にMono Suiteを導入可能な状態を確立する。
